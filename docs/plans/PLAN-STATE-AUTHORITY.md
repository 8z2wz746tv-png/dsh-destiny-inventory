# 物品状态的来源与权威（下一阶段协议）

2026-11-09 起草。**设计稿，未实施。** 基线 `b663911`（P1.5 冻结）。

上一阶段教会我们一件事：`ok` 和 `verified` 不是同一个东西，中间隔着一个真实的时间窗口。
这一阶段要把同一个问题问到底——**同一件物品的位置，谁有资格说？**

## 一、六种来源，各能证明什么

| 来源 | 能证明 | 不能证明 |
|---|---|---|
| **Bungie 快照** | 某一次读取时它在哪 | 一次尚未同步的写入的结果（实测滞后 60–80 秒） |
| **Pending 意图** | 用户要求它去哪、什么时候要求的 | 它已经到了 |
| **回滚位置** | 一次失败的写入之后，界面回到过哪里 | Bungie 现在说的任何话 |
| **Journal** | 发生过哪些操作、各自的结论 | 它现在的实际位置 |
| **Agent Context** | 构建那一刻面板上是什么样 | 构建之后发生的任何变化 |
| **IndexedDB 缓存** | 上一次成功读取的画面 | 现在 |

**这六种都不等于"位置"。** 只有经过核验的观测才接近事实，而那也只是"某一刻的事实"。

## 二、四个消费者现在各自在读什么

这是查代码查出来的，不是设计意图：

| 消费者 | 代码 | 实际读的 | 属于 |
|---|---|---|---|
| **库存面板** | `applyOverlay(snapshot.items, pending)` | 渲染后的行 `locationKey` | **effective** |
| **详情卡** | `item-detail.ts` → `item.location` | `ProfileItem.location`，**没有叠 overlay** | **observed** |
| **Agent view** | `view-reporter.ts` → `picked.locationKey` | 面板渲染后的行 | **effective** |
| **Agent journal** | `context.recent()` | 操作历史 | 历史 |
| **Context Builder** | 同上 ViewContext | 面板渲染后的行 | **effective** |

**两个发现**：

1. **详情卡是唯一读 `observed` 的消费者**——所以它和面板会对同一件物品说不同的话。
   这不是 bug，是没人规定过它们该不该一致。
2. **Agent 看到的是 `effective`**。用户拖了一件还没核验的东西，agent 那边显示它在目标位置——
   它拿这件事去回答"我的枪在哪"时，说的是**一个从未被观测到的位置**。

第二点比第一点严重：面板的不一致用户自己能看见（格子在这儿、卡上说那儿），
agent 的不一致它自己看不见。

## 三、核心问题：谁有权决定"有效展示位置"

现在实际上有三个人在回答"它在哪"：

```
observed  （快照）     ─┐
pending   （意图）     ─┼─→ effective（渲染）─→ 面板、agent view、context
rollback  （回滚）     ─┘
```

**协议是一句话**：

> **`effective` 是渲染产物，不是事实。任何消费者都不许把它当成"位置"读取。**

它只回答"这一格画在哪儿"。问"物品在哪"，必须回到 `observed`，并附带"有没有未完成的意图"。

## 四、每个消费者该声明自己读哪一种

| 消费者 | 该读 | 该说的话 |
|---|---|---|
| **库存面板（格子）** | `effective` | 无声。格子位置就是意图 |
| **详情卡** | `observed` + `pending` | 「在仓库」；有未核验意图时补「正在移往猎人，尚未确认」 |
| **Agent view** | `observed` + `pending` + `rollback` **分开报** | 三个字段各自有名字，不合成一个 `location` |
| **Context Builder** | 同 Agent | 同上 |
| **Journal** | 不变 | 历史事实 |

**这条要求会改线格式**：`ItemDetailView.location` 现在是单个字符串，要拆成
`observed` + `pending?`；`ViewContext.selected.location` 同理。这是破坏性变更，按本仓规矩
旧键一个不留。

## 五、冲突时的判定规则

同一物品三种位置并存时（这是常态，不是边缘情况）：

| 情形 | 格子画在 | 详情卡说 | Agent 说 |
|---|---|---|---|
| 只有观测 | observed | 「在 X」 | observed = X |
| 观测 + 未核验意图 | **意图的目标** | 「在 X，正在移往 Y」 | observed=X，pending→Y |
| 观测 + 回滚位置 | **回滚位置** | 「在 X」+**未确认标记** | observed=X，rollback→Y |
| 观测 = 意图目标 | 目标（无环） | 「在 X」 | observed=X |

**第三行是现在的缺口**：回滚位置既不是观测也不是 Pending，没有任何标记，
所以详情卡会说「在仓库」而格子画在猎人，**两边都不提"这是一个失败操作留下的位置"**。

## 六、这会引出什么

按上面的协议，最少要动三处：

1. **线格式**：`ItemDetailView.location` → `{ observed, pending?, rollback? }`；
   `ViewContext.selected` 同理。
2. **`effective` 不再对外**：`view-reporter` 报 `observed` + 意图，不报渲染结果。
3. **回滚位置要有名字**：`confirmMove` 落的位置必须能被识别成 `rollback`，
   而不是伪装成观测。

第 3 条是 P1.5 留下的那个缺口，现在它有了归属——**它不是"写路径的债"，
是"位置没有第三种名字"的债**。

## 七、这轮不做什么

| 不做 | 为什么 |
|---|---|
| 改 `ItemRow` 加字段 | 格子只需要 `effective`，加字段会让渲染层也开始区分，得不偿失 |
| 让详情卡也叠 overlay | 那会让"卡上说的"和"Bungie 说的"再也分不开——现在能分开恰恰是它的价值 |
| 给 Agent 一个"查某件物品"的新工具 | 先把已有的 view 报对，再谈新工具 |
| 持久化任何一层 | 这个协议的前提是"每层都说自己知道什么"，不是"多存一份" |

## 八、验证方式（实施后）

| 场景 | 期望 |
|---|---|
| 拖一件未核验的物品，看详情卡 | 说「在仓库，正在移往猎人」，不说「在猎人」 |
| 同一时刻问 agent「这件在哪」 | 答 observed，并说明有未确认的意图 |
| 写入被拒后看详情卡 | 说「在 X」，并带未确认标记（现在没有） |
| 缓存上屏、网络未回时问 agent | 不把缓存当事实 |
| `pending` 核验完成后 | 详情卡和 agent 都回到单一位置 |

## 九、一句话

**位置不是一种状态，是一种主张。** 谁主张，就要说清自己凭的是什么、以及自己不知道什么。
