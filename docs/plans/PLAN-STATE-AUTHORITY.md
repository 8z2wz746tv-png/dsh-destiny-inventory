# 物品状态的来源与权威（下一阶段协议）

2026-11-09 起草。**设计稿，未实施。** 基线 `b663911`（P1.5 冻结）。

上一阶段教会我们一件事：`ok` 和 `verified` 不是同一个东西，中间隔着一个真实的时间窗口。
这一阶段要把同一个问题问到底——**同一件物品的位置，谁有资格说？**

## 一、六种来源，各能证明什么

| 来源 | 能证明 | 不能证明 |
|---|---|---|
| **Bungie 快照** | 某一次读取时它在哪 | 一次尚未同步的写入的结果（实测滞后 60–80 秒） |
| **Pending 意图** | 用户要求它去哪、什么时候要求的 | 它已经到了 |
| **回滚位置** | 一次失败的写入之后，界面回到过哪里 | Bungie 现在说的任何话 |
| **Journal** | 发生过哪些操作、各自的结论 | 它现在的实际位置 |
| **Agent Context** | 构建那一刻面板上是什么样 | 构建之后发生的任何变化 |
| **IndexedDB 缓存** | 上一次成功读取的画面 | 现在 |

**这六种都不等于"位置"。** 只有经过核验的观测才接近事实，而那也只是"某一刻的事实"。

## 二、四个消费者现在各自在读什么

这是查代码查出来的，不是设计意图：

| 消费者 | 代码 | 实际读的 | 属于 |
|---|---|---|---|
| **库存面板** | `applyOverlay(snapshot.items, pending)` | 渲染后的行 `locationKey` | **effective** |
| **详情卡** | `item-detail.ts` → `item.location` | `ProfileItem.location`，**没有叠 overlay** | **observed** |
| **Agent view** | `view-reporter.ts` → `picked.locationKey` | 面板渲染后的行 | **effective** |
| **Agent journal** | `context.recent()` | 操作历史 | 历史 |
| **Context Builder** | 同上 ViewContext | 面板渲染后的行 | **effective** |

**两个发现**：

1. **详情卡是唯一读 `observed` 的消费者**——所以它和面板会对同一件物品说不同的话。
   这不是 bug，是没人规定过它们该不该一致。
2. **Agent 看到的是 `effective`**。用户拖了一件还没核验的东西，agent 那边显示它在目标位置——
   它拿这件事去回答"我的枪在哪"时，说的是**一个从未被观测到的位置**。

第二点比第一点严重：面板的不一致用户自己能看见（格子在这儿、卡上说那儿），
agent 的不一致它自己看不见。

## 三、核心问题：谁有权决定"有效展示位置"

现在实际上有三个人在回答"它在哪"：

```
observed  （快照）     ─┐
pending   （意图）     ─┼─→ effective（渲染）─→ 面板、agent view、context
rollback  （回滚）     ─┘
```

**协议是一句话**：

> **`effective` 是渲染产物，不是事实。任何消费者都不许把它当成"位置"读取。**

它只回答"这一格画在哪儿"。问"物品在哪"，必须回到 `observed`，并附带"有没有未完成的意图"。

## 四、每个消费者该声明自己读哪一种

| 消费者 | 该读 | 该说的话 |
|---|---|---|
| **库存面板（格子）** | `effective` | 无声。格子位置就是意图 |
| **详情卡** | `observed` + `pending` | 「在仓库」；有未核验意图时补「正在移往猎人，尚未确认」 |
| **Agent view** | `observed` + `pending` + `rollback` **分开报** | 三个字段各自有名字，不合成一个 `location` |
| **Context Builder** | 同 Agent | 同上 |
| **Journal** | 不变 | 历史事实 |

**这条要求会改线格式**：`ItemDetailView.location` 现在是单个字符串，要拆成
`observed` + `pending?`；`ViewContext.selected.location` 同理。这是破坏性变更，按本仓规矩
旧键一个不留。

## 五、冲突时的判定规则

三种位置可以同时存在，这不是边缘情况，是常态。下面是**穷举**，不是举例——
每一行都要能对应到代码里的一个分支，对着不上的就是没定义清楚。

### 渲染优先权

```
pending.target  >  rollback.at  >  observed
```

**新意图覆盖旧回滚**：用户拖过一次失败（回滚到 hunter），又拖一次（去 warlock），
那么界面跟着 **warlock**，不是 hunter。理由是 `rollback.at` 只是"上一次失败后停在这儿"，
而 `pending.target` 是"用户现在要它去哪"——后者永远更新。

### 五种组合

| # | observed | pending | rollback | 格子画在 | 详情卡说 | Agent 报 |
|---|---|---|---|---|---|---|
| 1 | vault | → hunter | — | hunter + 环 | 「在仓库，正在移往猎人」 | `observed: vault, pending → hunter` |
| 2 | vault | — | hunter | **hunter + 未确认** | 「在仓库」+ **未确认**（这是失败操作留下的位置） | `observed: vault, rollback: hunter` |
| 3 | vault | → warlock | hunter | **warlock + 环** | 「在仓库，正在移往术士」 | `observed: vault, pending → warlock, rollback: hunter`（rollback 降为历史） |
| 4 | hunter | → hunter | — | hunter（**有没有环取决于观测时刻**） | 「在猎人」 | `observed: hunter, pending → hunter` |
| 5 | warlock | → hunter | — | hunter + 环（冲突中） | 「在术士，有一条未完成的移动指向猎人」 | `observed: warlock, pending → hunter` |

**第 3 行是这张表的重点**：两个意图同时存在时，渲染跟新的那个，但**旧的没有被删除**——
它降级成一条历史，Agent 仍然能看到"曾经回滚到 hunter"。删掉它等于抹掉一次失败的痕迹。

**第 4 行要单独说**：观测与目标一致，**不等于**可以确认。确认的条件是
「这次读的 `startedAt` 严格晚于操作的 `submittedAt`」——同一毫秒的读不算（P1.5 已经这么做）。
所以第 4 行有两种子情况，界面上必须分得开：

| 观测与目标一致，且读发起于操作之后 | 无环，overlay 移除 |
| 观测与目标一致，但读发起于操作之前 | **仍有环**——那次读看不见这次操作 |

### rollback 什么时候消失

它不是一个新状态，是一条**有来源的临时位置**。三个失效条件，任一命中就不再控制渲染：

| 条件 | 为什么 |
|---|---|
| `observed === rollback.at` | 事实追上了。它不再需要标记，可以和观测合一 |
| 出现同物品的 `pending` | 新意图接管（第 3 行） |
| 超过核验期限（与 `VERIFY_TTL_MS` 同源，5 分钟） | 一次失败的操作不该永远占着界面 |

**rollback 不许伪装成观测**。它落到格子上的时候必须带未确认标记，否则详情卡（读 `observed`）
和格子会各说一套，而两边都不提"这是失败留下的位置"——这正是 P1.5 留下的那个缺口。

### 实现落点（2026-11-10）

四条不变量已经落进代码，`tests/state-authority.test.ts`。

**`ItemRow` 没有新增字段**——格子只需要知道自己该不该戴环，不需要知道环的来历。
来历由两处承担：

| 问题 | 答案在哪 |
|---|---|
| 这一格现在是回滚位置吗 | `ItemRow.pending === 'unconfirmed'` |
| 它是哪次失败留下的 | journal 里那条 `failed` 记录 |

所以"新意图接管但不抹除历史"这条：接管之后行上的标记没了，**历史在 journal 里**，
agent 仍然看得到。行是渲染态，journal 是事实——这正是整份协议的分工。

**`confirmMove` 加了 `source: 'observed' | 'rollback'`，默认 `observed`。**
默认值是刻意的：忘记传的调用方会"诚实地当作观测"，而不是悄悄把每个位置都标成未确认。
反过来（默认 rollback）会让正常回读的格子永远戴环，注入 B 盯着这条。

### 时钟语义

所有时间戳来自**同一台机器的同一个 `Date.now()`**：journal 的 `at` 由 host 打，
`submittedAt` / `startedAt` 由浏览器打。本插件是本地部署，两者同源，可以直接比较。

**如果将来出现跨机器部署（远程宿主 + 本地浏览器），这条前提就没了**，
混合时钟下的先后判断需要重新论证——届时不能再用墙上时钟证明因果关系。

### 一条不是规则的规则

上表里每一行的"详情卡说"和"Agent 报"**都不是措辞问题**。格子画在 hunter、详情卡说 vault，
这不叫不一致，叫两个消费者在回答两个不同的问题：

- 格子回答「我现在把意图画在哪儿」
- 详情卡回答「Bungie 最后一次说它在哪儿」

真正的问题是**没有一个消费者告诉用户这两件事同时成立**。第 1 行那句
「在仓库，正在移往猎人」就是这个协议要交付的东西——不是把两个值统一，是把它们**都说出来**。

## 六、这会引出什么

按上面的协议，最少要动四处：

1. **线格式**：`ItemDetailView.location` → `{ observed, pending?, rollback? }`；
   `ViewContext.selected` 同理。
2. **`effective` 不再对外**：`view-reporter` 报 `observed` + 意图，不报渲染结果。
3. **回滚位置要有名字**：`confirmMove` 落的位置必须能被识别成 `rollback`，
   而不是伪装成观测。它需要携带来源（哪次失败、从哪儿回滚、什么时候），
   否则只是给原来的模糊状态换了个标签。
4. **详情卡的措辞**：`observed` 与 `pending` 同时存在时要说两句话，不是一句。

第 3 条是 P1.5 留下的那个缺口，现在它有了归属——**它不是"写路径的债"，
是"位置没有第三种名字"的债**。

## 七、这轮不做什么

| 不做 | 为什么 |
|---|---|
| 改 `ItemRow` 加字段 | 格子只需要 `effective`，加字段会让渲染层也开始区分，得不偿失 |
| 让详情卡也叠 overlay | 那会让"卡上说的"和"Bungie 说的"再也分不开——现在能分开恰恰是它的价值 |
| 给 Agent 一个"查某件物品"的新工具 | 先把已有的 view 报对，再谈新工具 |
| 持久化任何一层 | 这个协议的前提是"每层都说自己知道什么"，不是"多存一份" |

## 八、验证方式（实施后）

| 场景 | 期望 |
|---|---|
| 拖一件未核验的物品，看详情卡 | 说「在仓库，正在移往猎人」，不说「在猎人」 |
| 同一时刻问 agent「这件在哪」 | 答 observed，并说明有未确认的意图 |
| 写入被拒后看详情卡 | 说「在 X」，并带未确认标记（现在没有） |
| 缓存上屏、网络未回时问 agent | 不把缓存当事实 |
| `pending` 核验完成后 | 详情卡和 agent 都回到单一位置 |

## 九、一句话

**位置不是一种状态，是一种主张。** 谁主张，就要说清自己凭的是什么、以及自己不知道什么。
