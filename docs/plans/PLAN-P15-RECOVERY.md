# P1.5 · 跨刷新的操作状态恢复

2026-11-09。**设计稿，未实施。** 基线 `49f471e`。

起因是 2026-11-07 的实测：一次成功的写入（journal 记 `ok`），F5 之后面板显示旧位置，
最长约 80 秒才追上。而缓存把这段滞后展示得更快——2319ms 的白屏变成了 42ms 的错误位置。

**这份文档只回答"恢复到什么程度、按什么规则"，不写实现。** 三个问题（恢复哪些记录、
显示哪个位置、连续操作怎么办）定了再动手。

## 一、先钉死三个术语

这三个混在一起，设计一定会走偏。

| 事实 | 含义 | 能不能当作"已落地" |
|---|---|---|
| journal 的 `result: 'ok'` | Bungie **接受了这次写请求** | ❌ 不能 |
| Bungie 快照里的位置 | 某次读**观测到的**位置 | ❌ 不能，有 60–80 秒滞后 |
| `verified` | 回读确认位置与目标一致 | ✅ 这才是 |

实测证据：`超星系团 vault → hunter` 的 journal 是 `ok`，而 Bungie 在 20/40/60 秒时
仍然报 `vault`，80 秒才变。**`ok` 与"物品已经在那儿"之间隔着一条 60–80 秒的河。**

由此推出 P1.5 的第一条原则：

> **恢复的是操作意图（overlay），不是重放写请求（TransferItem）。**
> 恢复过程里绝不重新发起写入——那需要幂等保证，我们还没有。

顺带区分四个容易混为一谈的东西：

- **重放操作**：再向 Bungie 发一次写。这轮不做。
- **恢复意图**：把"用户想做但没被确认的事"重新挂回内存。**这轮做的**。
- **恢复 overlay**：界面按意图画。是恢复意图的结果，不是独立功能。
- **核验**：确认 Bungie 是否真到了。已有 `reconcile`，这轮不重写。

## 二、问题 A：恢复哪些 journal 记录

### 恢复阶段什么都不判断

初稿这里写的是"恢复前先看当前快照，位置已经等于目标就记 verified、不恢复"。**那是错的**，
而且正好违反本文第八节。

缓存里可能是旧位置。用它判断"已经落地"，等于让一条过期观测冒充核验结论——正是这一路
在防的东西。

**恢复阶段只做一件事：把意图挂回内存。** 不读快照判断，不写 verified 转换。

判断"到没到"只有一个地方：新鲜网络快照回来之后，由 `reconcile` 做。如果那时物品已经在
目标位置，`reconcile` 自然就把这条操作确认掉了——不需要恢复阶段预先插一手。

### 一次拖拽不是一条记录，是一条链

初稿说"同一物品取最新的合格候选"。这个算法有个隐藏后果：

```
A: vault → hunter   ok，无 resolution
B: hunter → warlock failed
```

B 被"failed 被排除"这条过滤掉，于是 A 成了"最新合格候选"，在下次 F5 被恢复。

从代码看这很自然，从语义看它是**背着人做了决定**：用户的最后一次意图是 warlock，
B 失败了，他想要的东西退回到 hunter——但这不是"因为 B 不合格所以 A 上位"能描述的事，
而是一条明确的回滚规则。让恢复算法顺手把这件事办了，就是把没定义清楚的东西藏进实现里。

所以先定义链：

**一条链 = 同一件物品在一段时间内的连续操作，按 `at` 升序。**

每个物品的恢复答案由链的**末尾**决定，而不是由"过滤后剩下谁"决定：

| 链末尾的形状 | 当前有效意图 | 恢复 | 恢复后状态 |
|---|---|---|---|
| 最后一条是 `ok`，无 `resolution`，在期限内 | 就是它 | 是 | `verifying` |
| 最后一条是 `ok`，它之后有 `failed` | **仍是它** | 是 | `verifying` |
| 最后一条是 `ok`，它之后有更新的 `ok` | 更新那条 | 只它一条 | `verifying` |
| 最后一条是 `failed`，之前没有任何 `ok` | 无 | 否 | — |
| 最后一条 `ok` 已有 `resolution` | — | 否 | — |
| 最后一条 `ok` 已超过期限 | — | 否 | — |
| 来源是 `external` | — | 否 | — |

**"失败不取消上一次成功意图"这条要写明白**，因为它有两个相反的读法：

- 读法一（采用）：用户拖 A 成功、拖 B 失败，他想要的是**回到 A 的位置**。所以 A 仍是有效意图。
- 读法二（否掉）：B 失败说明 A 的前提也不成立，A 也该作废。

采用读法一的理由：B 失败后 `send-action` 本来就会把行写回 `B.from`（也就是 A 的目标），
界面已经在表达"A 的位置是当前状态"。恢复阶段如果不同意，两处就会打架。

读法一的代价必须写清：**如果 A 其实从来没成功，恢复出来的意图就是错的**。这时用户会看到
物品在 hunter 带未确认环——然后约 60–80 秒后，`reconcile` 发现观测一直在 vault，
`mismatches` 累积，转 `unknown` 再 `superseded`，画面自己纠正。

**短暂显示一个可能错的意图，比让一次成功看起来从未发生要好。** 这是取舍，不是疏忽。

### 期限：总期限，刷新不续命

初稿拿 `VERIFY_TTL_MS`（5 分钟）当恢复窗口，但没说清恢复之后还剩多少时间。

采用**总操作期限**：从 journal 里那条记录的 `at` 起算，最多 5 分钟。恢复时

```
submittedAt = entry.at          // 原始提交时刻，不重置
expiresAt   = entry.at + VERIFY_TTL_MS
```

**刷新不给旧操作续命。** 一条提交于 4 分 50 秒前的操作，恢复之后只剩 10 秒——
10 秒内没有一致观测，它就转 `unknown`，再过一阵转 `superseded`。

这是对的：五分钟前的一次拖拽，不该在五分钟后的新页面上继续要求被相信。
如果 Bungie 的同步窗口（实测 60–80 秒）还没走完它就过期了，那是**如实反映**——
我们确实不知道它成没成。

顺带澄清 `VERIFY_TTL_MS` 的性质：它是**清理机制**（把悬而不决的操作收进 `unknown`），
不是"操作失败"的判据。`unknown` 之后还有 `superseded` 兜底。

**到期之后会发生什么，要说全**（初稿只说了"转 unknown"）：

1. 到期**不删除** Pending，只是把状态从 `verifying` 换成 `unknown`——界面继续显示目标位置，
   但带"未确认"标记，不声称成功。
2. `unknown` 的操作**仍然参与** `reconcile`。如果之后哪怕一次新鲜快照与目标一致，
   它照样转 `verified` 并移除。**迟到的正确观测可以翻案**，这是允许的、也是对的。
3. 如果连续两次观测都稳定地落在别的、新的位置，转 `superseded` 并停止控制界面。

   **"两次"必须是两次不同的新鲜观测**，不能是同一份快照被处理了两遍——否则一次请求重试、
   一次重复 load、或者一次缓存回放，就能凑出"两次稳定"。判定要落在观测的 `startedAt` 上：
   只有 `startedAt` 严格递增的两条观测才算两次。

**竞态**：`reconcile` 是同步函数，到期判断与观测比对在同一个调用里顺序执行——
先看这次有没有一致观测（有就直接 `verified`），再考虑过期。所以不存在"同一时刻既过期又被确认"。
这个顺序在实施时必须保持：**先核验，后过期**。反过来的话，一条本该被这次读确认的操作会先被判成
`unknown`，白白多挂一轮。

### 幂等：两层，不能只靠"只读"

初稿写"恢复只读 journal，天然幂等"。**这个推导不成立。**

只读的是持久化那一侧——不写 journal、不重发 Bungie 请求，这层确实幂等。但恢复还会**改内存**：
往 `PendingOps` 里塞一条 operation。同一次页面生命周期里 `load-inventory` 可能触发多次，
每次都会读到同一条记录。

所以幂等要在内存层单独保证：

- **稳定的身份**：`eventId = restore:<at>:<instanceId>`。同一条记录永远是同一个 id。

  读取时要做的是**折叠（Journal Entry Reduction），不是去重**——同一 `(at, instanceId)` 的两行
  是"原始快照"与"带 resolution 的最终态"，保留任一行都会丢东西：留第一行丢修正，留第二行
  （如果它被后续覆盖过）可能丢原始字段。折叠规则：**按 `(at, instanceId)` 分组，取带
  `resolution` 的那行；没有则取组内最后一行。** 因为 `resolve()` 是把改过的同一个对象重新
  序列化，所以带 `resolution` 的那行是完整最终态。

  这个复合键够不够稳，查过真实数据（54 条 move 记录）：

  - `(at, instanceId)` 在 jsonl 里**看起来重复**——那是同一条记录的原始行与它的
    `resolution` 修正行（append-only 的第二行）。**按 `(at, instanceId)` 去重即得一条操作。**
  - 同一物品两次**不同**操作之间的最小间隔是秒级（写入串行，中间隔着一次网络往返），
    不存在同一毫秒产生两条不同 move 的可能。
  - `external` 来源的记录会出现同毫秒多条（`detect-external` 一轮记多条），但它们不参与恢复。

  所以这层唯一性成立**有前提**：只对 `source === 'ui'` 的 move 生效，且读取时必须先按
  `(at, instanceId)` 去重。前提变了（比如以后写队列改成并行），这个键就要重新论证。
- **已经在场就不动**：`restore` 进来先看这个物品当下的 operation——
  - 没有 → 创建
  - 有，且 `eventId` 相同 → **什么都不做**（不重置 `submittedAt`、不重新分配 `seq`）
  - 有，且 `eventId` 不同（用户在恢复后又拖了一次）→ **什么都不做**，新的那条说了算

第二条是关键：重置 `submittedAt` 会让一条本该过期的操作重新获得核验资格，
重置 `seq` 会让它盖掉用户的真实操作。

## 五、需要动的东西（实施时才做）

| 位置 | 改动 | 为什么 |
|---|---|---|
| `context-store` 的 journal 记录 | 可能要加 `verifiedAt` 之类的字段 | 否则判据 3 只能靠"没有 `resolution`"间接表达（**够用，先不加**） |
| `agent-tools` 的 journal 读取 | 需要能按物品 + 时间窗筛 | 恢复要在一次请求里拿到候选，不能拉 200 条让前端过滤 |
| `load-inventory` | 缓存上屏后、网络回来前，插入恢复步骤 | 恢复发生在"用户已经能看到东西"的时候，而不是更早 |
| `pending-ops` | 加一个 `restore(entry)` 方法 | 用 journal 的 `at` 当 `submittedAt`，状态置 `verifying` |

**`restore` 的语义要写清楚**：它构造一个"已经被接受、等待观测确认"的操作，
**不产生任何写入，不产生 journal 记录**。

## 六、这轮明确不做

| 不做 | 为什么 |
|---|---|
| 重放写请求 | 需要幂等保证，而 `TransferItem` 没有幂等键 |
| 把 `ok` 当 `verified` | 实测已经证明两者差 60–80 秒 |
| 恢复 lock / equip | 它们没有"目标位置"这个可展示的意图 |
| 跨设备恢复 | 缓存和 overlay 都是浏览器本地的；换设备等于换一个人 |
| 持久化 overlay 本身 | 恢复从 journal 读即可，不需要第三份状态 |

## 六点五、七种链形状的完整状态转移

一张表把「输入 → 恢复什么 → Pending → 界面 → 之后」串起来。**这是实施前的最后一道关**：
每一行都要能对应到代码里的一个分支，对应不上的就是没定义清楚。

前提：链按 `at` 升序、同一物品、`source` 都是 `ui`、只考虑 `move`。

| # | 链（最后一条在右） | 恢复 | Pending 状态 | `effectiveLocation` | 界面 | 之后 reconcile |
|---|---|---|---|---|---|---|
| 1 | `A(ok, 无 resolution, 未超期)` | A | `verifying`，`submittedAt=A.at` | `A.to` | 目标位置 + 未确认环 | 观测==`A.to` → `verified`，环消失；一直不等 → `unknown` → `superseded` |
| 2 | `A(ok) → B(failed)` | A | `verifying`（同 #1） | `A.to` | 目标位置 + 未确认环 | 同 #1。B 的存在**不改变**任何一格 |
| 3 | `A(ok) → B(ok)` | 只 B | `verifying`，`submittedAt=B.at` | `B.to` | B 的目标 + 环 | 观测==`B.to` → `verified`。A 不进 Pending、不产生转换 |
| 4 | `A(failed)`（之前无 ok） | 无 | 空 | `observed` | 观测位置，无环 | 无 |
| 5 | `A(ok, 已有 resolution)` | 无 | 空 | `observed` | 观测位置，无环 | 无（结论已由 resolution 给出） |
| 6 | `A(ok, 已超期)` | 无 | 空 | `observed` | 观测位置，无环 | 无 |
| 7 | `A(external)` | 无 | 空 | `observed` | 观测位置，无环 | 无 |

恢复之后用户又拖一次（记作 C），是这七行之外最需要写清的一格：

| 情形 | Pending | `effectiveLocation` | 之后 |
|---|---|---|---|
| 恢复 A 后，用户拖 C（从 `A.to` 出发） | 被 C 覆盖（`seq` 更大，`eventId` 不同） | `C.to` | 观测==`C.to` → `verified`。A 不再有 Pending，也不再产生转换 |
| C 写入被明确拒绝 | 空（C 被 settle 移除） | **`C.from`**（= `A.to`），**且应带 `pending: 'unconfirmed'`** | 见下面的漏洞说明；下次 F5 时 A 会被重新恢复成 `verifying` |
| C 的结果不明（超时） | `C` 转 `verifying` | `C.to` | 走既有回读；回读一致 → `verified` |

### 这张表要守的不变量

每条都能用一条测试钉住，实施时逐条对照：

1. 同一物品在 `PendingOps` 里**最多一条** operation。
2. 恢复过程**不产生任何 Bungie 写请求**（可用「恢复期间 `postAction` 零调用」断言）。
3. 恢复**不重置** `submittedAt`（用 4m50s 那条例验：恢复后剩余时间约 10s，不是 5 分钟）。
4. 旧操作的观测**不能结束**新操作的 Pending（`startedAt <= submittedAt` + `eventId` 认领）。
5. **缓存不产生 `verified`**（缓存那一趟根本不调 `reconcile`）。
6. **失败操作不被"过滤后让旧操作上位"**：判据永远是链末尾，不是过滤结果。
7. **Pending 消失 ≠ Bungie 已核验**：`failed` 移除 Pending，但那是"确定没执行"，不是"确认到位"。

第 6、7 条是这次修订的核心。上一版这里写的是"它们不会让测试变红，只能靠写代码时记着"——
**那句是退让，不是事实。** 两条都能变成可执行断言：

- 第 6 条：构造 `A(ok) → B(failed)`，断言恢复结果是 **A**；再构造 `A(ok) → B(failed) → C(ok)`，
  断言恢复结果是 **C**。然后注入"删掉链末尾判据、退回按结果过滤"，两者都必须变红。
- 第 7 条：构造一条明确失败的操作，断言 Pending 被移除、**没有产生 `verified` 转换**、
  且失败结果没有被当成"已核验位置"。注入"把 failed 当 verified"，必须变红。

补充一个只靠"两次稳定"才能暴露的用例：**同一份快照喂两遍**，不能让它从 `unknown`
转成 `superseded`。

## 七、验收（实施后要跑）

| 场景 | 期望 |
|---|---|
| 写入 → 5 分钟内 F5 | 物品显示在**目标位置**，带未确认环，约 80 秒后环消失 |
| 写入 → 6 分钟后 F5 | 不恢复；显示 Bungie 当前位置（此时通常已同步，看起来是对的） |
| 写入 → 已同步 → F5 | **不恢复**（位置已等于目标），也不该有未确认环 |
| 写入 → F5 → 再拖同一件 | 新操作的 `from` 是目标位置，不是原位置 |
| 写入 → F5 → 再拖 → 新操作失败 | 撤到**前一个意图**的位置，不是撤到 Bungie 的旧位置 |
| journal 里有 `failed` 的记录 | 不恢复 |
| journal 里有 `external` 的记录 | 不恢复 |
| 连续 F5 三次 | 只恢复一次的效果，不叠加、不重复 |
| **A 成功、B 失败，再 F5** | 恢复的是 A（链末尾唯一的 ok），且不因为 B 被过滤而"意外上位" |
| **恢复后重复调用 restore** | 不重复创建、不重置 `submittedAt`、不重新分配 `seq` |
| **A 恢复后执行 B、B 失败** | 行回到 A 的目标位置；此时 PendingOps 里没有 overlay（甲方案），下次 F5 再恢复 A |
| **A 提交后 4 分 50 秒才 F5** | 恢复但只剩约 10 秒核验时间，之后转 `unknown`——不续命、不假装还有五分钟 |
| **缓存说目标位置、Bungie 说旧位置** | 缓存不参与核验；以 reconcile 的观测为准 |
| **A、B 连续提交、A 的观测迟到** | A 的迟到观测不能结束 B 的 Pending（`startedAt <= submittedAt` 与 `eventId` 认领共同保证） |

## 七点五、协议总表（每一阶段允许什么、禁止什么）

| 阶段 | 允许 | 禁止 |
|---|---|---|
| 缓存上屏 | 展示旧快照 | 用缓存判断操作是否落地 |
| Journal 恢复 | 按链末尾找出有效意图 | 重放写请求；写 `verified` 转换 |
| Pending 恢复 | 创建 `verifying` 状态，`submittedAt` 取原始 `at` | 重置提交时间；重新分配 `seq` 覆盖更新的操作 |
| 新鲜快照返回 | 交给 `reconcile` 判断 | 用"位置相等"绕过 reconcile 直接确认 |
| 操作 B 失败 | 按链规则处理（行回 B 的起点；A 仍是有效意图） | 无条件复活 A，或把"A 上位"当成规则 |
| 核验完成 | 结束 Pending、产生转换 | 把 `ok` 直接升级成 `verified` |

## 七点五五、两个已测量的边界（2026-11-09，实施后补查）

不是猜测，是测出来的行为。改这两处之前先看这一节。

### 边界一：`/journal` 只返回最近 200 条

`ContextStore.recent(200)` 是**接口返回上限，不是完整性保证**。而且一行修正记录占一个名额，
所以 200 行买不到 200 条操作（实测 200 行 = 100 条操作）。

**截断的后果是"不恢复"，不是"恢复错的"**：如果同一物品的 A(`ok`) 被挤出窗口、只剩
B(`failed`)，链里没有任何 `ok`，`pickRestorable` 返回空。

它**不会**退回"拿最后一条当意图"——这条退化被测试盯着（见 `recovery-limits.test.ts`）。
代价是：链的另一半在窗口外时，那次操作不会出现在界面上，只能等 Bungie 的真实位置。

### 边界二：`settled` 只活在内存里

重启后 `settled` 清空，同一批 journal 会被重新评估一次。**绝大多数情况下答案是稳定的**，
因为链归并靠的是 journal 本身：

- `A(ok) → B(ok)`：链末尾是 B，重启前后都恢复 B。
- `A(ok) → B(failed)`：链末尾找不到比 A 更新的 `ok`，恢复 A。

但有一个**真实存在的不一致**，必须记下来而不是当它不存在：

```
会话一：A 恢复 → 用户拖 B → B 被拒 → A 进 settled → 那格没有环
重启后：B 失败不影响 A 的资格 → 链末尾仍是 A → 那格又带上环
```

**显示的位置一样（都是 A 的目标），但环的状态不同。** 这不是错误——A 确实成功过、
物品确实在那儿——但它是一次"重启改变了界面标记"。

要不要持久化 `settled`，取决于这个差异值不值得：把内存集合搬进 IndexedDB 会引入
第三个需要和 journal 保持一致的状态，而 journal 本身已经能推出结论。**暂不做，但记着。**

## 七点六、已知缺陷（不由 P1.5 解决）

这两条是**在 P1.5 之前就存在**的，不要因为 P1.5 的测试全绿就当成已修。

| 缺陷 | 表现 | 归属 |
|---|---|---|
| **回滚位置没有标记** | 写入被明确拒绝后，行被 `confirmMove(from)` 写到"上一意图的位置"，但这个位置既不是观测也不是 Pending，没有未确认环。此时库存面板显示 Hunter，详情卡（读快照）显示 Vault，两处自相矛盾 | 写路径（P1.2/P1.3 范围），不是恢复逻辑 |
| **`ok` 无法区分"已核验"** | journal 里成功的操作永远没有 `resolution`，"从未核验"与"核验通过"在数据上看不出区别 | 数据形状（P1.5 之后若要长期依赖，需要单独的字段） |

## 七点七、实施顺序

按依赖顺序，每阶段一个提交：

| 阶段 | 内容 | 核心验收 |
|---|---|---|
| P1.5.1 | Journal 读取与折叠 | 同一操作的两行折叠成一条，且不丢 `resolution` |
| P1.5.2 | 操作链归并 | 链末尾决定恢复意图；七种形状逐条断言 |
| P1.5.3 | `PendingOps.restore()` | 幂等、不重置提交时间、不写 journal |
| P1.5.4 | `load-inventory` 接入 | 缓存展示与恢复的先后顺序正确 |
| P1.5.5 | reconcile 与 TTL | unknown 仍可核验；核验先于过期（有测试） |
| P1.5.6 | 连续操作验收 | A/B 覆盖、失败回滚、迟到观测不污染 |

## 八、写给实施者的一句

恢复这条路上最容易犯的错，是**在恢复的时候顺手做一次核验**然后把它当结论——
那又回到了"用一条可能过期的读去确认一次操作"。

恢复只负责**把意图挂回去**；核验永远只发生在网络快照回来之后，由 `reconcile` 做。
