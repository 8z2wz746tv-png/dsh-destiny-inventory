# P1.5 · 跨刷新的操作状态恢复

2026-11-09。**设计稿，未实施。** 基线 `49f471e`。

起因是 2026-11-07 的实测：一次成功的写入（journal 记 `ok`），F5 之后面板显示旧位置，
最长约 80 秒才追上。而缓存把这段滞后展示得更快——2319ms 的白屏变成了 42ms 的错误位置。

**这份文档只回答"恢复到什么程度、按什么规则"，不写实现。** 三个问题（恢复哪些记录、
显示哪个位置、连续操作怎么办）定了再动手。

## 一、先钉死三个术语

这三个混在一起，设计一定会走偏。

| 事实 | 含义 | 能不能当作"已落地" |
|---|---|---|
| journal 的 `result: 'ok'` | Bungie **接受了这次写请求** | ❌ 不能 |
| Bungie 快照里的位置 | 某次读**观测到的**位置 | ❌ 不能，有 60–80 秒滞后 |
| `verified` | 回读确认位置与目标一致 | ✅ 这才是 |

实测证据：`超星系团 vault → hunter` 的 journal 是 `ok`，而 Bungie 在 20/40/60 秒时
仍然报 `vault`，80 秒才变。**`ok` 与"物品已经在那儿"之间隔着一条 60–80 秒的河。**

由此推出 P1.5 的第一条原则：

> **恢复的是操作意图（overlay），不是重放写请求（TransferItem）。**
> 恢复过程里绝不重新发起写入——那需要幂等保证，我们还没有。

顺带区分四个容易混为一谈的东西：

- **重放操作**：再向 Bungie 发一次写。这轮不做。
- **恢复意图**：把"用户想做但没被确认的事"重新挂回内存。**这轮做的**。
- **恢复 overlay**：界面按意图画。是恢复意图的结果，不是独立功能。
- **核验**：确认 Bungie 是否真到了。已有 `reconcile`，这轮不重写。

## 二、问题 A：恢复哪些 journal 记录

### 判据

一条记录进入恢复候选，**同时**满足：

1. `action === 'move'` —— 只有 move 有位置意图；lock/equip 没有"目标位置"可恢复。
2. `result === 'ok'` —— 明确失败的（`failed`）不恢复。
3. **没有 `resolution`** —— 有 `resolution` 说明回读已经给了结论，不管结论是什么。
4. `at` 在 **5 分钟**以内 —— 超过就不恢复（理由见下）。
5. `source !== 'external'` —— 外部变更不是用户的操作意图，没有"想让它去哪"。

### 为什么是 5 分钟

和 `pending-ops` 的 `VERIFY_TTL_MS` 一致。超过这个窗口再恢复，等于让面板声称
"五分钟前那次拖拽还没完成"——它多半早就完成了，只是当时的进程没看见。

**代价要说清**：如果用户在 5 分钟内没刷新、6 分钟后才 F5，那次操作不会被恢复，
物品会显示 Bungie 当前的位置（那时通常已经同步完了，所以显示是对的）。

### 一个现有字段的缺口

journal 里**没有"是否已核验"这个信息**。`resolution` 只在失败回读时写，
成功的操作永远没有它。

所以判据 3 实际上是"**从来没有被核验过**"，而不是"核验失败"。这是对的——
因为恢复的目的就是把没核验过的接上。但要在文档里写明：**`ok` + 无 `resolution`
读作"未核验"，不是"已成功"**。

### 幂等

F5 三次会读到同一条记录三次。因为**恢复只读 journal、不写任何东西**，
天然幂等，不需要额外的操作 ID。

唯一需要防的是"恢复后又核验了、然后又恢复"。解法：恢复前先看当前快照——

> 如果物品现在的位置**已经等于**那条记录的目标位置，说明它落地了：
> 记一条 `verified` 的转换（P1.5 顺手补上），**不恢复**。

这一步同时回答了"重复 F5 会不会反复显示未确认"——不会，第二次就认出来了。

## 三、问题 B：显示目标位置还是原位

**显示目标位置，并明确标记为待核验。**

理由：用户刚刚亲手发起了它，journal 也有成功回执。继续显示原位，就是告诉用户
"你那次操作没发生"——这正是这次实测里最伤人的地方。

但目标位置**不是事实**，界面必须能区分三种东西：

| 状态 | 画在哪 | 标记 |
|---|---|---|
| Bungie 观测到的位置 | 观测位置 | 无 |
| 本地恢复的意图（未核验） | **目标位置** | 未确认环 |
| 核验通过 | 目标位置（Bungie 也这么说） | 无环，overlay 移除 |

这正是 `applyOverlay` 现有的行为（`pending: 'applying' | 'unconfirmed'`），
**不需要新机制**，只需要把恢复出来的操作喂进同一个 `PendingOps`。

**恢复出来的操作初始状态**：`verifying`（不是 `submitted`，也不是 `succeeded`）。
因为它已经有过一次成功的回执，现在等的是观测。

## 四、问题 C：60–80 秒内再拖一次

这是决定整个设计可靠性的地方。分四步看。

### C1 · 新操作的起点

A：`vault → hunter`（恢复出来的，画在 hunter）。
用户接着拖 B：从 hunter 拖到 warlock。

B 的 `from` 应该是 **hunter**——面板当前显示的位置，也就是"当前有效的操作状态"。

**这一点现有架构已经对了**：`move()` 拿的 `from` 是渲染后的 `item.locationKey`，
而渲染已经叠过 overlay。所以 B 的起点自动是 hunter，不需要新代码。

但要写成约束钉住：**`from` 必须取自渲染结果，永远不许回读 Bungie 快照去推断起点。**
否则 B 会被记成 `vault → warlock`，把一个从来没被观察过的中间态当成事实。

### C2 · B 的写入会不会因为 Bungie 还停在 vault 而失败

会，而且这是**已知且正确**的失败：Bungie 只知道物品在 vault，让它从 hunter 转出，
它会拒绝（我们的 `move-item` 用 `from` 解析源角色，Bungie 那边对不上）。

**这时的行为必须诚实**：B 失败 → overlay 撤掉 B → 回写到 B 的 `from`（hunter）→
因为 A 的意图还在，物品继续显示在 hunter，带未确认环。

用户看到的：拖到 warlock 没成，东西还在 hunter，标着"不确定"。
而不是"东西回到 vault 了"。

### C3 · A 的结局是什么

A 被 B 覆盖了（同一物品，`PendingOps` 只留最新一条）。所以 A 不会再有 transition。

**这是可以接受的**：A 的中间位置（hunter）从来不是一个需要长期成立的结论，
用户实际想要的是 B 的最终位置。**只核验最终意图，不核验历史中间态。**

但要注意 A 在 journal 里仍然是 `ok` 且无 `resolution` ——**它会在下一次恢复时
被当成候选**。所以还需要一条：**同一物品的多条候选，只恢复最新的一条**
（按 `at` 排序取最后一条 move）。

### C4 · 迟到的旧观测会不会污染新操作

`pending-ops` 的 `startedAt <= submittedAt` 规则已经挡住了"读发起于操作之前"的情况。

但恢复场景有新的时间关系：**恢复出来的操作，`submittedAt` 来自 journal 的 `at`**，
而当前这次 load 的 `issuedAt` 一定更晚，所以能通过时间检查 ✓。

真正危险的是反过来：**B 提交后，A 那次写入的同步刚好完成，Bungie 报 hunter**。
这时 B 的观测是 hunter，目标是 warlock → 不一致 → B 记一次 mismatch。
这是对的，不算污染——它只是还没到。

Bungie 最终会变成 warlock，B 确认。

**要防的是另一种**：A 的同步完成让物品从 vault 变成 hunter，而**B 的 overlay 已经因为
别的原因此刻不在了**，于是面板显示 hunter——看起来像"回到了 A 的中间态"。
但只要 overlay 在，B 的目标位置优先，不会被观测带走。这也是现有规则。

## 五、需要动的东西（实施时才做）

| 位置 | 改动 | 为什么 |
|---|---|---|
| `context-store` 的 journal 记录 | 可能要加 `verifiedAt` 之类的字段 | 否则判据 3 只能靠"没有 `resolution`"间接表达（**够用，先不加**） |
| `agent-tools` 的 journal 读取 | 需要能按物品 + 时间窗筛 | 恢复要在一次请求里拿到候选，不能拉 200 条让前端过滤 |
| `load-inventory` | 缓存上屏后、网络回来前，插入恢复步骤 | 恢复发生在"用户已经能看到东西"的时候，而不是更早 |
| `pending-ops` | 加一个 `restore(entry)` 方法 | 用 journal 的 `at` 当 `submittedAt`，状态置 `verifying` |

**`restore` 的语义要写清楚**：它构造一个"已经被接受、等待观测确认"的操作，
**不产生任何写入，不产生 journal 记录**。

## 六、这轮明确不做

| 不做 | 为什么 |
|---|---|
| 重放写请求 | 需要幂等保证，而 `TransferItem` 没有幂等键 |
| 把 `ok` 当 `verified` | 实测已经证明两者差 60–80 秒 |
| 恢复 lock / equip | 它们没有"目标位置"这个可展示的意图 |
| 跨设备恢复 | 缓存和 overlay 都是浏览器本地的；换设备等于换一个人 |
| 持久化 overlay 本身 | 恢复从 journal 读即可，不需要第三份状态 |

## 七、验收（实施后要跑）

| 场景 | 期望 |
|---|---|
| 写入 → 5 分钟内 F5 | 物品显示在**目标位置**，带未确认环，约 80 秒后环消失 |
| 写入 → 6 分钟后 F5 | 不恢复；显示 Bungie 当前位置（此时通常已同步，看起来是对的） |
| 写入 → 已同步 → F5 | **不恢复**（位置已等于目标），也不该有未确认环 |
| 写入 → F5 → 再拖同一件 | 新操作的 `from` 是目标位置，不是原位置 |
| 写入 → F5 → 再拖 → 新操作失败 | 撤到**前一个意图**的位置，不是撤到 Bungie 的旧位置 |
| journal 里有 `failed` 的记录 | 不恢复 |
| journal 里有 `external` 的记录 | 不恢复 |
| 连续 F5 三次 | 只恢复一次的效果，不叠加、不重复 |

## 八、写给实施者的一句

恢复这条路上最容易犯的错，是**在恢复的时候顺手做一次核验**然后把它当结论——
那又回到了"用一条可能过期的读去确认一次操作"。

恢复只负责**把意图挂回去**；核验永远只发生在网络快照回来之后，由 `reconcile` 做。
